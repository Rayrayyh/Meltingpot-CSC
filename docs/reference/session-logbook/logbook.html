Two failure modes, sixty-five notes

memory/decisions and memory/lessons

The 18 lessons are not 18 different mistakes. Cluster them and almost all collapse into two, plus a third that is the environment rather than the code.

A truth checked once is assumed permanent

Five lessons are the same error wearing different clothes: a row validated at creation and assumed still valid, a header trusted because it was there, a function body re-emitted from memory instead of read, a ledger entry pointing at a parent that vanished. Every one is a snapshot mistaken for a fact. This is where the schema is fragile.

What you see is not what is serving

Five more describe a stale layer between the change and the observation: a rebuild under a running server, a production build emptying the dev cache, a route handler that does not know its own host, a social card swapped in place that stays cached, a fixed element captured by a transform. Every one cost a debugging session aimed at the wrong layer.

Seven lessons say the environment, not the code, was the most reliable source of failure: egress TLS blocking the browser, container binaries, test data bleeding between runs. The most recent, lesson 018, is the one that let the real Clerk component be rendered at all.

The three habits that cost the most

Tuning one property per round. Six messages over eight minutes to move one image; roughly fifteen turns over two days on the card tilt, thrown away when you pasted the values. Each round is a full render and review cycle. Handing over the target values, or a range to bracket, collapses ten rounds into one.

Describing a reference instead of attaching it. "It was another one, look for it" cost two failed searches for a video. It resolved the moment you attached the file. The same pattern repeats with the hero pot, which you eventually committed yourself.

Preferences stated once, then restated. Four rules had to be given twice with visible irritation: mp4 video, one deploy target, stay on the branch, and the copy voice. You solved this yourself in the end, and it is the best instruction in the whole session: Store these instructions in a reasonable place so they outlive your context window.

One thing worth flagging

A credential a vendor dashboard asks for should travel from you into that dashboard, not through a chat transcript on the way. A transcript is not a secret store: it persists, it is summarized, and tooling reads it back later. Where a setup step seems to need a secret key in the conversation, paste it into Netlify or the vendor’s own field instead, and rotate anything that has already gone the other way. You asked for a sweep for exposed keys early on, so the instinct was already right; it is the handling under time pressure that slips.
